## 2. The ruled guard shape does not work

The write-boundary guard was ruled to *"assert against the row's own provenance, not the ambient context."* I checked that against the real data **before** building it:

```
row_tenant                      batch_owner                     provenance_mismatch   n
Anna and Associates             Anna and Associates             false                 16
Nassau Harbour Consulting Ltd.  Nassau Harbour Consulting Ltd.  false                 16
```

`Transaction.BusinessId == ImportBatch.BusinessId` in **every** case.

That guard would have passed cleanly through this breach — the same way the reverted Order 4 guard would have, and for the same reason: **the two things being compared agree, and are wrong together.** I have not built it.

## 3. No downstream invariant can catch this class

If the wrong id is set at **batch creation**, everything downstream inherits it consistently. There is no disagreement to detect.

The check has to sit at **context resolution**, or compare against something **outside the system's own resolved state** — which is a heuristic, not an invariant.

---

## 4. The reading you need to give

**(a) Product defect** — the circuit context genuinely resolved to Anna while the operator had Nassau selected: a stale context, a switch that did not take, a `bid` not applied.

**(b) Operator action on the wrong client** — the context was legitimately Anna and the file was uploaded there. The product cannot infer a file's intended tenant from its name, so it had no basis to object.

They need **different fixes**. (a) is a context-resolution bug. (b) is a missing confirmation before a batch commits into a named client.

**I am not asserting which**, because the audit trail that would distinguish them is exactly what F-251 says does not exist for that window.

> **This is the entanglement worth naming: F-251 is not merely *beside* F-247, it is *blocking its diagnosis*.** Closing the silent write paths first would make the next occurrence answerable instead of ambiguous.

---

## 5. One structural finding that stands either way

The tenant check lives on the **audit path, not the write path**, and it fails open.

- `AuditPreSignValidator` is invoked from exactly one place — `ImmutableAuditLedgerService.RecordEventAsync`.
- `TransactionRepository` never calls it. **Nothing checks tenant attribution on a transaction write.**
- The check only happens as a side effect of emitting an audit event, and it skips silently when the circuit context is unresolved — a state whose own comment names background and batch contexts.

That accounts for all three observed facts: the batch resolved wrong; all 16 rows were written because writes have no guard; and row 8's audit emit ran with a resolved context, detected the mismatch and **threw** — which is why there are **zero audit events**.

**The detection destroyed the evidence.** A fail-closed guard on the audit path, with no guard on the write path, converts a tenant breach into a silent one.

---

## 6. What I recommend regardless of the reading

**A confirmation naming the target client before a batch commits.** It protects against both readings, and it is the only control that would have stopped this specific event.
