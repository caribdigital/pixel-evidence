## 1. F-253 / #4165 — the enumeration you asked for, and it found something else (HEADLINE)

Cass ruled that the credit-note reason taxonomy comes to you before any code moves, on the concern
that the in-app dialog "feeds posting through its own mapping", so credit notes created in-app may
**post differently** from ones imported and resolved through the ruled J1 gate.

I did the enumeration. **That concern does not hold in the form stated — and what is actually
happening is worse.**

### The two taxonomies

| | Creation path | Import / review path |
|---|---|---|
| Field | `CreditNote.Reason` (`CreditNoteReason`) | `Transaction.CreditNoteAdjustmentBasis` |
| Entity | `Domain.Entities.CreditNote` | `Web.Data.Entities.Transaction:376` |
| Surface | `CreateCreditNoteDialog.razor` | `CreditNoteBasisDialog.razor` |
| Values | **9** | **2** |

**The 9:** GoodsReturned · PricingError · Discount · DuplicateInvoice · Cancelled · QuantityError ·
VATRateError · DamagedGoods · Other

**The 2 (your sealed J1 set):** ConsiderationChanged · OverchargeCorrection

### The posting each produces

`VATReturnGenerator.CreditNoteMovesL4` (lines 287–300) is the **only** place the L4 decision is
made, and it is fail-closed:

```csharp
return sale.CreditNoteAdjustmentBasis switch
{
    ConsiderationChanged  => true,   // L4 moves with L7
    OverchargeCorrection  => false,  // L7 only
    _ => throw new InvalidOperationException(
        "Credit note transaction {id} is Processed with no adjustment basis. " +
        "The basis is captured, never inferred ...")
};
```

So the 9-value `Reason` **produces no posting at all**. It is never read by the generator. Your
sealed basis is the sole input, and a missing basis throws rather than guesses. On that narrow
question the engine is behaving exactly as you sealed it.

### What is actually wrong

`CreditNoteService.CreateCreditNoteAsync` (lines 85–123) writes **only** a `CreditNote` row. It does
not create a `Transaction` with `Category="CreditNoteIssued"`, and it never sets
`CreditNoteAdjustmentBasis`.

Nothing applies it afterwards:

- `VATReturnGenerator` never reads the `CreditNotes` table at all.
- `CreditNote.AppliedToVATReturn` exists on the entity, in the EF configuration and in migrations —
  and is **never set or read by any application code**.
- Every non-test, non-migration reference to `.CreditNotes` is confined to `CreditNoteService`, the
  `CreditNotes.razor` listing page, `DevSeeder`, and one line in `Transactions.razor`.

**A credit note created through the in-app dialog therefore has no effect on any VAT return.** It
produces a document, an audit entry and a PDF. The only credit notes that reach a return are
`Transaction` rows carrying a sealed basis, which arrive via import.

### Why this is worse than the labelling question

It is not two mappings disagreeing. It is **one path that posts and one that does not post at all**
— and the non-posting one is the path that presents a practitioner with nine regulatory-looking
options that read as though they are driving a treatment.

A practitioner who issues a credit note in-app for "Goods Returned" has every reason to believe the
adjustment is captured. It is not. The return computes without it, **silently** — no held row, no
refusal. Your fail-closed guard cannot fire, because there is no `Transaction` for it to fire on.
The guard is sound; nothing ever reaches it.

### What I need from you

1. **Must an in-app credit note post at all**, or is document-only the intended behaviour with the
   import path as the sole ledger route? This is the question that decides the rest.
2. If it must post, it has to acquire a sealed basis — meaning the 9-value list either **maps onto**
   your 2 sealed bases or is **replaced** by them.
3. `GoodsReturned` specifically, which is what Cass flagged: a return of goods is a change in
   consideration and would have to move **both L7 and L4**.

### My uncertainty, stated plainly

I traced this by enumerating every reference to the `CreditNotes` table and confirming the generator
never touches it. If there is an application path I did not find — a background job, a manual
reconciliation step — the conclusion changes. **I would rather you had someone check my reasoning
than take it on trust.** Nothing has been changed in code.

## 4. F-255 — shipped, and it found a hole in a guard you care about

Cass ruled the lodgement audit entry. The entry read:

> "VAT return {id} **confirmed as lodged with DIR** on {date}. Method: DirOnlinePortal.
> Reference: **(none)**."

Three defects: it asserts the DIR-side act the product cannot observe; the method was a **UI
default**, not a user statement; and `(none)` is an internal null rendered as customer-facing text.

**The finding was the coverage gap, not the string.** The REQ-MSG-001 guard sweeps Razor components
and CSS. It does not look at text a service builds at runtime and persists. So it rejected "lodged
with the Department" in a dialog draft one day, while the durable audit record asserted the DIR-side
act unchallenged. That guard now covers audit-event construction, pinned by test.

Two details in your lane:

- The scope Cass set is **every durable regulatory record including the outbox payload**
  (#3990–#3992). The structured operator log is explicitly out of scope and keeps its engineering
  phrasing, with a comment saying so.
- A test at `Fw002Tests:266` was asserting `"(none)"` was **present** — a test holding the defect in
  place as firmly as it could have held a fix. It is inverted, not deleted.

**And a mistake of mine worth your attention, because it is an audit-integrity point.** My first cut
also removed the return identifier from the description. The Reef caught it as a Must-Not-Ship RED.
The reason matters: **the audit-logs grid has no target column** — Timestamp, Event Type, Action,
User, Details, Severity, IP. Details was the only place a practitioner could see which return an
entry refers to. Without it, two lodgements by the same actor on the same day are indistinguishable
on the page someone opens to ask what happened. The identifier is restored and pinned as a presence.

Filed but not built: that grid should carry a target column, so scoping a regulatory record does not
depend on an id embedded in prose.
